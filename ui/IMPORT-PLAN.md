## “OpenCode Rune”: verified identity and fit

The likely referent is [anomalyco/rune](https://github.com/anomalyco/rune), not Svelte runes or the unrelated Rune scripting language. The name match is strong, but raygen has not confirmed the exact project URL. Upstream's README describes it as a native GPU-rendered Rust UI framework for macOS, Windows, Linux and the web, with a pre-release API and revision-pinned Git dependencies.

Read authoritative upstream README, core README, rune-kit README, Cargo workspace and web example on 2026-11-07. The observed `dev` head was [99c123d6](https://github.com/anomalyco/rune/commit/99c123d6b2127d1226c72dec37919e51019142ff); the web example at that revision is Rust compiled via `wasm-bindgen`, not React/Solid DOM components.

- [Core docs](https://github.com/anomalyco/rune/blob/99c123d6b2127d1226c72dec37919e51019142ff/crates/rune/README.md): keyed trees, focus/input, headless PNGs, tree dumps, scripted input and hot-patching are useful for agent verification. AccessKit exposes native OS accessibility. Browser accessibility equivalence was not established by this research; do not infer it from native support. The docs note the web host sets no cursors yet.
- [rune-kit](https://github.com/anomalyco/rune/blob/99c123d6b2127d1226c72dec37919e51019142ff/crates/rune-kit/README.md): reusable controls, cards, virtualized tables, Markdown and an app shell. Its `Kit` owns semantic palette, typography, radius, elevation, motion and glyph tokens. `rune-theme-opencode` is a separate theme, not a requirement to copy OpenCode's appearance. The Table reports grid/row/columnheader/gridcell roles, not HTML table elements.
- [Web example](https://github.com/anomalyco/rune/blob/99c123d6b2127d1226c72dec37919e51019142ff/examples/web-hello/src/lib.rs): demonstrates the same Rust view/state machinery on wasm. It does not establish production browser/mobile parity for Computah.

Updated direction: raygen selected a Rune native/local-Pi experiment, separate from faithful design integration. This supersedes the earlier DOM/React preference, not the preserved Figma authority. Keep document/registry wire data renderer-neutral. Rune has excellent agent inspection but does not itself supply an untrusted extension sandbox. A native table is a real interactive grid, not HTML; require proper roles, sorting, navigation and records rather than prose, and do not claim DOM semantics. The experiment should prove a reusable restaurant card, long table, IME/clipboard, native accessibility and recovery. This planning lane installed no Rune dependency and ran no Rune build; confirmed APIs below are source evidence, not a demonstrated Computah application.

### Presence: preserve simulation, replace only rendering

`ui/pixel-presence.html` is the preserved behavioral oracle. Native Rune does not execute its HTML/Canvas2D script. Do not silently replace it with an orbiting icon, a video loop, generic spring animation or 120 independent UI layout springs.

1. Port the simulation as an isolated deterministic state object: 96 core +24 fringe particles, fixed seeded grain/noise, original home positions, fringe wander scale0.65, confinement, spring32/drag10, state-weight blending, level attack/release, pointer lean and bounded delta stepping. Keep the five named presets and explicit normalized input. Preserve reset/advance semantics for fixtures. JavaScript doubles versus Rust floats can change exact pixels; initially use f64 for simulation and convert at paint, compare trajectories within a stated tolerance rather than promising cross-renderer hash equality.
2. Keep particle identities/velocity across state transitions. Rune `AppSpec::poll` and `Tx::wake_after` are confirmed scheduling hooks; implement bounded updates and redraw only while the study is active/visible and motion is allowed. Investigate exact occlusion/visibility lifecycle before claiming battery behavior; stop simulation rather than catching up an unbounded hidden interval. Reduced motion should settle the selected pose and input level, with a named status exposed once—not announce every particle/frame.
3. Prototype native paint separately: Rune has shape/canvas geometry, rounded quads, transforms, subtree blur and low-level `Blend::PlusLighter`. Original bloom is blurred layers plus additive composition and a crisp foreground. Similar-looking primitives do not guarantee the same HSL/sRGB/compositing result. Determine whether grouped primitives plus blur/additive layers match; otherwise use a bounded custom compositor. Account for source ellipse squish/orientation, blur extent, DPI and clipping. Do not spend effort embedding a webview just to avoid a simulation port without an explicit platform/security decision.
4. Gate replacement with identical reset/state/level/time scenarios and sampled particle trajectories, then inspect side-by-side stills and motion recordings against original at DPR1/2. Test all five states, input0/1, pause/resume, reduced motion and pointer leave; verify stable dense core and fringe, aperiodic travel and no clipping. Original HTML remains the review surface until the native port passes; a static approved pose may be an explicitly labelled interim fallback, not advertised as finished v6 motion.

The upstream framework's `Spring::new(duration,bounce)` is not numerically the study's spring32/drag10 integrator. Likewise its dissolve compositing is a useful primitive, not proof of full bloom equivalence. These distinctions are essential to a faithful identity port.

## Proposed renderer-neutral contracts

These are concrete implementation recommendations, not claims that the Figma design already implements this architecture. Architecture integration owns Effect Schema wire definitions and portable JSON fixtures. Export compatible JSON Schema for persisted documents and registry props where needed; derive renderer types/validators from that source rather than maintaining competing wire definitions. The field names below are proposed requirements until reconciled with the shared contract.

### Document and edits

- `SurfaceDocument`: `schemaVersion`, `revision`, `themeRef`, `registryRevision`, `routes`, `rootNodeId`, and a node map. `rootNodeId: null` with an empty node map is valid, including when every component has been deleted. Navigation, composer, widgets, panels, empty states and app shell are ordinary removable nodes, not secretly hardcoded exceptions.
- Each node has a stable `id`, exact versioned `componentRef`, validated `props`, named child slots, explicit data bindings, and action references. Keep persisted UI configuration separate from fetched records and transient selection/focus state. Bindings use data-source IDs and constrained field selectors, not executable expressions.
- Agent operations include inspect/export, insert, patch, move, remove, register/replace/unregister components, edit tokens, preview and restore. Apply a batch atomically against `baseRevision`; stale edits return a conflict and current revision instead of overwriting another actor's changes.
- Validate tree shape, references, slot/prop schemas, token references, data/action capabilities and document budgets before activation. Cycles, dangling children and incompatible registry removals fail with actionable diagnostics; removing all dependent nodes and their component in the same transaction is valid.

### Registry and reusable generated designs

- Registry entries contain namespaced `id`, immutable `version`, `propsSchema`, slot definitions, renderer implementation/artifact hash, compatible document versions, required capabilities, semantic/accessibility obligations, theme token dependencies and fixture cases. Keep a discoverable catalog describing when to use each design.
- Agents first search by semantic intent and compatible schema, then reuse an existing exact component version. A newly generated design is validated and registered once; future uses reference it. Version changes are explicit and existing surfaces stay pinned until migrated. Equivalent names do not silently resolve to new code.
- `data.table@1`: typed columns with stable IDs, label, field selector, format/alignment, optional sorting/filtering/pagination, stable row IDs, empty/loading/error states. ### Rendering, extension and action boundary

Trusted built-ins render validated documents; structured data is never evaluated as code. A generated design may compose existing nodes without code execution. New executable extensions require a real isolation boundary: for web, a separate-origin sandboxed frame with a narrow validated message bridge, resource/network limits and no ambient parent/session credentials; for native, an isolated process or constrained runtime rather than an in-process arbitrary plugin. A Rust crate and a CSS selector are not sandboxes. Prefer data-only composition until executable extensions are genuinely needed.

Action IDs map to host capabilities with validated argument schemas. A component can request an action, not authorize itself. Preview resolves synthetic/read-only data and records effect requests without executing them. External content, photos, records and extension output cannot edit the UI policy or grant capabilities. Permission to customize UI is not permission to change external services or expose secrets.

### Safe preview, activation and recovery without prompt spam

1. Agents edit a draft freely within granted workspace scope, including deleting all components. Validate it and render in an isolated preview against deterministic safe fixtures; do not ask for approval for each token, card or layout edit.
2. Automatically activate ordinary authorized, reversible UI-only changes after schema, accessibility and interaction checks. Atomically switch the active revision only after a successful render. Unknown/incompatible registry versions and render failures keep the current revision active and return diagnostics; failed preview never overwrites it.
3. Retain last-known-good snapshots and an audit history outside the active document/registry, with one-step undo and revision restore. Deleting UI must not delete user data or history. Deleting every component remains a valid intentionally blank app, not a reason to resurrect defaults without consent.
4. Provide a separate recovery entry point owned by the host (for example a recovery route and host command/API). It can inspect history, restore or load a new document even with no app components. Keep it outside the generated app's mount, theme and extension origin so broken CSS/code or a removed composer cannot hide it. Clearly document this as operational recovery, not a mandatory undeletable application component.
5. Ask only at actual authority boundaries: external effects not already granted, credential/policy changes, permanent data/history deletion or shared publication. A UI label saying “approved” cannot replace host authorization. Rendering a preview never invokes live side effects.
